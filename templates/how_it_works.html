How It Works

An overview of the hybrid encryption architecture used to protect your documents.

1. Hybrid Encryption

Secure Digital Locker combines symmetric encryption (AES-256-GCM) and asymmetric encryption (RSA-OAEP) into a hybrid cryptosystem.

Why Symmetric Encryption for the Document?

Symmetric ciphers like AES are exceptionally fast, computationally lightweight, and designed to encrypt data of any size efficiently without ciphertext expansion.

Why Asymmetric Encryption for Key Protection?

Asymmetric cryptography solves the key distribution problem. Instead of storing or sharing the symmetric key directly, the system protects the AES key using the locker's public key. Only someone with the corresponding private key can recover it.

2. Core Cryptographic Components

AES-256-GCM

Authenticated Encryption

Advanced Encryption Standard operating in Galois/Counter Mode (GCM). It provides both confidentiality (encryption) and integrity / authenticity (tamper detection) simultaneously.

Random AES Key

256-bit Document Key

A fresh 256-bit (32-byte) key is generated independently for each document using a cryptographically secure pseudo-random number generator (CSPRNG). Keys are never reused between files.

GCM Nonce

12-byte Initialization Vector

A unique 12-byte (96-bit) nonce (number used once) generated per encryption. The nonce ensures that encrypting identical documents produces completely distinct ciphertexts.

Authentication Tag

16-byte GMAC Tag

A 16-byte cryptographic checksum computed by AES-GCM over the ciphertext and nonce. It proves the ciphertext was created with the authentic key and has not been altered.

RSA-OAEP

Asymmetric Key Wrapping

RSA-OAEP is used to securely protect the random AES-256 document key. The RSA public key is used for protection, and the corresponding private key is required to recover the AES key.

RSA Key Pair

Public & Private Keys

When you upload a document, the locker performs hybrid encryption through these distinct stages:

  1. Key Generation: The server generates a fresh 256-bit AES key using a cryptographically secure random number generator.
  2. Document Encryption: AES-256-GCM encrypts the document, creating the ciphertext, a 12-byte nonce, and a 16-byte authentication tag.
  3. Key Protection: The locker's RSA public key encrypts the AES key using RSA-OAEP.
  4. Storage: Only the encrypted ciphertext is saved to disk (.enc). The nonce, authentication tag, and encrypted AES key are stored in the database. The raw AES key is immediately cleared from memory.

4. Decryption Flow (View & Download)

When an authorized user with the correct 6-digit Locker PIN accesses a document, the reverse process executes:

             ENCRYPTED AES KEY
                      │
                      ▼
                   RSA-OAEP
             (using RSA Private Key)
                      │
                      ▼
                 AES-256 KEY
                      │
                      │
                      ▼
             ENCRYPTED DOCUMENT + Nonce + Auth Tag
                      │
                      ▼
                 AES-256-GCM
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
    Verify Auth Tag      Original Document
       (GMAC check)             │
            │                   ▼
   ✓ Untampered: Accept   SERVED TO USER
   ✗ Modified: Reject
  1. Access Control: The user enters their 6-digit Locker PIN, which verifies authorization before cryptographic operations begin.
  2. Key Recovery: The locker's RSA private key decrypts the encrypted AES key using RSA-OAEP.
  3. Document Decryption: AES-256-GCM decrypts the ciphertext using the recovered AES key, the 12-byte nonce, and the 16-byte authentication tag.
  4. Integrity Check: AES-GCM verifies that the authentication tag matches the ciphertext. If any bit was modified, decryption halts immediately.
  5. Delivery: The decrypted document is served to the user in-memory. Decrypted plaintext is never saved permanently to disk.

5. How AES-GCM Detects Tampering

Standard ciphers (like AES in CBC or CTR mode) only provide confidentiality — they do not inherently detect if an attacker changed bytes in the encrypted file. AES-GCM solves this by computing a Galois Message Authentication Code (GMAC):

The Authentication Tag: During encryption, AES-GCM evaluates an algebraic polynomial over Galois Field GF(2128) using the ciphertext and nonce. Even if an attacker changes a single byte or single bit of the ciphertext, the computed authentication tag will no longer match the stored tag, causing AES-GCM decryption to fail immediately and reject the corrupted data.
